# Changelog

Release notes of autoreview, newest first. Unreleased changes are fragments
under `changelog.d/`; `scripts/changelog fold` moves them here.

## 0.6.0 - 2026-11-16

### Added

- Each release also publishes `autoreview-<version>-aarch64-apple-darwin.tar.gz` for Apple Silicon Macs on macOS 14 or newer, with its `.sha256` file and a build provenance attestation. The binary is ad-hoc signed and not notarized; `scripts/macos-check archive <archive>` checks the checksum, the attestation, the signature and the version on a Mac. ([#513](https://github.com/pohunekd/autoreview/issues/513))
- `scripts/setup` sets up autoreview on a Mac with Apple Silicon and macOS 14 or newer, with bash 4 or newer (`brew install bash`). It installs the `aarch64-apple-darwin` archives of autoreview and pohunek after their checksum and attestation checks, writes the configuration without `pohunek.runtime_dir` when `XDG_RUNTIME_DIR` is unset, refuses configuration and XDG directories in the folders that macOS privacy protection closes to launchd jobs, checks that the pohunek daemon finds Python 3.11 or newer for the reviewer adapters, and installs two LaunchAgents next to pohunek's: the review service and the hourly review queue from 08:00 to 20:00, with secrets only through `--env-file` and logs under `$XDG_STATE_HOME/autoreview/logs`. `scripts/macos-check service` checks the installed agents. ([#513](https://github.com/pohunekd/autoreview/issues/513))

### Changed

- `autoreview report --pipeline` now also covers pruned reviews: the prune keeps the report's counts per repository and pipeline, so a `--pipeline` range is no longer refused because it starts before the review retention. Besides the outcome-retention check, it refuses with `report_range_pruned` a range with a day that 0.4.0 or 0.5.0 pruned, because those days have daily counts but none per pipeline; reviews pruned by a release without the rollup count as zero. `stats` output is unchanged. ([#52](https://github.com/pohunekd/autoreview/issues/52))
- `scripts/setup` installs pohunek 0.43.1 when pohunek is missing or older than 0.41.0, so a fresh setup can fetch the pull request head at session start and run head-checkout reviews. A pohunek of 0.41.0 or later that is already installed is kept. ([#505](https://github.com/pohunekd/autoreview/issues/505))
- The product is named Šafář review in the README and the features page, as on pohunek.dev; the repository, the binary and command `autoreview`, the configuration and the release archive names are unchanged. ([#509](https://github.com/pohunekd/autoreview/issues/509))
- `autoreview profiles install --agent codex` on a host other than Linux, such as a Mac review host, fails with `profile_agent_unsupported` before it calls pohunek or writes a file, because the Codex adapter needs Linux `PR_SET_CHILD_SUBREAPER` to end the processes that Codex leaves. Claude reviewers install as before, and a policy may still name Codex reviewers on Linux hosts. ([#513](https://github.com/pohunekd/autoreview/issues/513))
- On macOS, `pohunek.runtime_dir` may be left out of `config.yaml`: autoreview then passes no `XDG_RUNTIME_DIR` to the pohunek CLI, which reaches its daemon in pohunek's macOS default directory, and `autoreview init` leaves the key out unless `--pohunek-runtime-dir` is given. On Linux the key stays required. ([#513](https://github.com/pohunekd/autoreview/issues/513))

## 0.5.0 - 2026-11-16

### Added

- **Breaking:** A recorded finding that is still open when its pull request is merged or closed now gets the outcome `open_at_merge` or `open_at_close` at the head the pull request ended on; the engine finds this with one state read per pull request that left the review search, at most once per `schedule.outcome_check_interval_seconds`. Every `config.yaml` now needs that key (for `scripts/env-to-config`, `HERMES_PR_REVIEW_OUTCOME_CHECK_INTERVAL_SECONDS`): add it in the same window as the new binary, since the engine refuses to start without it, and remove it again on a rollback, since earlier releases refuse it as unknown and open the store unchanged. ([#51](https://github.com/pohunekd/autoreview/issues/51))
- **Breaking:** The engine now records one row per published finding in the new store table `finding_outcomes`, with its reviewer, pipeline, rule, severity, confidence, head SHA and outcome (`open`, or `refuted` or `not_blocking` when the verifier demoted it); the record never changes a review or writes to GitHub. Every `config.yaml` now needs the key `store.outcome_retention_seconds` (for `scripts/env-to-config`, `HERMES_PR_REVIEW_OUTCOME_RETENTION_SECONDS`), the time a row stays after its last change: add it in the same window as the new binary, since the engine refuses to start without it, and remove it again on a rollback, since earlier releases refuse it as unknown and open the store unchanged. ([#51](https://github.com/pohunekd/autoreview/issues/51))
- **Breaking:** A pipeline with `intent_check: issues` hands the reviewers the issues that the pull request closes in its own repository and reports a clear mismatch with them as a blocking finding; issues of other repositories are never read, and the published review states what was compared. Every `config.yaml` now needs `limits.max_issue_characters` (for `scripts/env-to-config`, `HERMES_PR_REVIEW_MAX_ISSUE_CHARACTERS`): add it in the same window as the new binary, since the engine refuses to start without it and `autoreview validate` names it. A rollback to an earlier release must remove the key again, and `intent_check` from the policy's pipelines, because earlier releases refuse both as unknown. ([#56](https://github.com/pohunekd/autoreview/issues/56))
- `autoreview prune-branches --git-binary <PATH>` lists the review branches under `session.branch_prefix` that no review needs on the review hosts whose repositories are on this machine, and deletes them with `--yes`. It keeps every branch of a queued, running or awaiting review, of a review whose session cleanup is pending, of a pohunek session and of a worktree, and every symbolic ref, and prints each branch with its commit. `--host` picks one host, `--older-than-days` keeps recently finished reviews, and a failed deletion or a skipped `--host` host exits with status 1 (`branch_prune_incomplete`). ([#42](https://github.com/pohunekd/autoreview/issues/42))
- The new command `autoreview findings list --repo OWNER/REPO --since DATE` prints the recorded outcome of every finding of a repository published since midnight UTC of that day, oldest first, as one JSON object per line with the finding's key, reviewer, rule, severity, outcome, head SHAs and how its pull request ended. ([#51](https://github.com/pohunekd/autoreview/issues/51))
- A later published review now settles the recorded outcome of an earlier finding: `fixed` when it finds the finding fixed, or answered with the answer upheld by the verifier, and `answered` when the answer is not verified. A finding that is published again keeps its first row, which the review after it settles. ([#51](https://github.com/pohunekd/autoreview/issues/51))
- `autoreview report` prints the time from the review request to its first publication, once per request (median and p90, `request_to_publication_median_seconds` and `request_to_publication_p90_seconds` in the JSON, whose `schema_version` is now 2) beside the time from the attempt's creation. The request time is stored with each review that a review request starts and kept through pruning; label triggers and reviews stored by earlier releases have none and are left out. ([#52](https://github.com/pohunekd/autoreview/issues/52))
- `autoreview report --since DATE` prints the time from the creation of a review attempt to its publication, the shares of reviews approved without a human, waiting for one or requesting changes, the reviewer disagreement rate (published attempts where one reviewer made a blocking claim and another none, with the reviewers that blocked alone, kept through pruning), the verifier demotion rate per reviewer (blocking claims found not blocking or refuted, in percent of those checked, kept through pruning), and the outcomes of the published findings per reviewer, severity and repository, as JSON with `--json` or as a short text table. `--repo` and `--pipeline` narrow it to one repository or one policy pipeline. With `notifications.weekly_report: digest` in the policy, `autoreview review-queue` ends its message once a week with the report of the last 7 UTC days and today, also when nothing waits. ([#52](https://github.com/pohunekd/autoreview/issues/52))
- `autoreview guard scan` runs the prompt-injection guard offline over a JSONL corpus of pull request texts, with the bound and the scan of the review step, and prints each pull request's score, signal codes and suspect flag and a summary (flagged share, hidden-text and truncated counts, pull requests per signal). `scripts/guard-corpus` fetches such a corpus of closed pull requests through `gh api`, `examples/guard-lexicon.txt` is a starter lexicon, and `testdata/guard/injection-corpus.jsonl` a synthetic injection corpus. A new guide, "Enable the text guard", describes shadow mode, the measurement, the targets and when to move a rule from `log` to `await` or `comment`. ([#345](https://github.com/pohunekd/autoreview/issues/345))
- A policy rule with `guard` now runs the prompt-injection guard once per review, before the reviewers start. It reads the configured texts of the pull request with extra GitHub read calls (only for such a rule), up to `guards.text.max_input_bytes`, and stores the result with the review. A suspect pull request (its score reaches `threshold`, the read left text out, as at the byte bound or for a patch GitHub omits, or `guards.text` is missing) sends one `guard_suspect` message at level `action` with signal codes only. With `on_suspect: await` a clean review that the rule would approve waits for a human approval; with `comment` a request for changes on an untrusted author becomes a comment; `log` changes nothing else. A review without a guard is unchanged. ([#345](https://github.com/pohunekd/autoreview/issues/345))
- Policy rules accept an optional `guard` section (`fields`, `threshold`, `on_suspect`) and `config.yaml` an optional `guards.text` section (`max_input_bytes`, `lexicon_file`) for the prompt-injection guard. Both are validated at load, the lexicon file included, a rule with `guard` needs `guards.text`, and a `guard` changes the policy digest. A rollback to an earlier release must remove both sections again, because earlier releases refuse them as unknown. ([#345](https://github.com/pohunekd/autoreview/issues/345))

### Changed

- **Breaking:** Claude reviewer and verifier requests are now sent under the protocol name `autoreview-claude/v1` instead of `claude-otel-noninteractive/request-v1`, and the answer of a Claude adapter from 0.3.0 or earlier, which runs such a request as a plain prompt and answers in mode `text`, now stops the review with `review_adapter_outdated` instead of a retried `review_result_invalid`. Run `autoreview profiles install` for every Claude profile on every review host before this release is deployed; a review stopped on a missed host needs that reinstall and `autoreview retry`, and a rollback of the engine needs no reinstall. ([#392](https://github.com/pohunekd/autoreview/issues/392))
- **Breaking:** A Claude reviewer run that Claude Code ends on the rate or usage limit of its model account (a result message with `is_error`, subtype `success` and `api_error_status` 429) now fails with `reviewer_usage_limited` instead of keeping its code (`review_wrapper_invalid`, or `claude_result_invalid` on exit 0); Codex output names no structured limit, so Codex reviewers are unchanged. The scheduler tries such a review again after each delay of the new key `schedule.usage_limit_retry_delays_seconds` (the example's `[900, 1800, 3600, 3600, 3600, 3600, 3600]` covers 5 h 45 min) without spending `schedule.retry_delays_seconds`, and notifies only on the first limited attempt and when it stops. Every `config.yaml` now needs the key (for `scripts/env-to-config`, `HERMES_PR_REVIEW_USAGE_LIMIT_RETRY_DELAYS_SECONDS_JSON`): add it in the same window as the new binary, since the engine refuses to start without it and `autoreview validate` names it, and a rollback to an earlier release must remove it again because earlier releases refuse it as unknown. ([#461](https://github.com/pohunekd/autoreview/issues/461))
- `scripts/setup` installs autoreview 0.5.0 and passes `--pohunek-timeout-seconds` to every `autoreview profiles install` it runs. It takes the value from the new `--pohunek-timeout-seconds` flag, or asks once when a profile is missing; there is no default, and a value that is not a whole number of seconds above 0 stops the script with exit code 1. ([#286](https://github.com/pohunekd/autoreview/issues/286))
- autoreview now bundles SQLite 3.54.1 through `rusqlite` 0.41, which fixes RUSTSEC-2026-0459 (uninitialized memory read from a crafted write-ahead log). In both supported deployments autoreview opens only its own store, in a directory that no other user may write, so the advisory did not reach it; existing store databases open unchanged. ([#428](https://github.com/pohunekd/autoreview/issues/428))
- When `scripts/setup` upgrades an autoreview older than 0.4.0, it names each Codex profile that `autoreview profiles install` wrote earlier and prints the `profiles install` command that writes its adapter again, because 0.4.0 refuses every request to an earlier Codex adapter with `review_nonce_mismatch`. Setup keeps those profiles and does not know the flags of their first install, so the command holds placeholders for them. ([#435](https://github.com/pohunekd/autoreview/issues/435))
- A review whose stored input names a base branch outside the names that discovery accepts (1 to 255 ASCII letters, digits, `.`, `_`, `/` and `-`, without `..`) now fails with `review_input_invalid` before it builds a reviewer or verifier request, so the trusted `Base branch:` line can never hold a line break, U+0085, U+2028 or U+2029. Discovery refused such pull requests already, so reviews of GitHub pull requests are unchanged; an empty base branch of an older stored review is still accepted. ([#436](https://github.com/pohunekd/autoreview/issues/436))
- Discovery refuses a pull request whose base branch name GitHub allows but autoreview does not support (outside 1 to 255 ASCII letters, digits, `.`, `_`, `/` and `-`, or containing `..`) with its own code, `base_branch_unsupported`, instead of `github_response_invalid`; `candidates` lists it as rejected with that code, and a pull request already reported under the old code is reported once more. A stored review whose base SHA is not 40 lowercase hex digits, or whose pull request URL does not name its repository and number on the GitHub host, now fails with `review_input_invalid` before it builds a request; discovery refused such pull requests already, so reviews of GitHub pull requests are unchanged. ([#446](https://github.com/pohunekd/autoreview/issues/446))

### Fixed

- Codex reviewer runs on a `checkout: head` pull request now compare the repository skill folders with the trusted base again after the run, so a skill that a process of the head (for example a pohunek hook) left on disk during the run fails the review with `review_head_skills_refused` instead of being published. The change reaches a review host only when its profiles are installed again with `autoreview profiles install`. ([#462](https://github.com/pohunekd/autoreview/issues/462))
- A stopped review whose pull request one discovery pass did not list, for example after a failed author-permission read, is now withdrawn for that pass instead of dropped, so its return handles the stopping run again without a second `review_stopped` notice and a head that the usage limit or the head fetch mismatch bound stopped stays stopped; the daily `stopped` count counts that return again. An `autoreview retry` of a stopped head now still starts when a withdrawal, or a retarget away to a base branch that no run completed and back, comes before its first run; before, either one could stop the head again. ([#466](https://github.com/pohunekd/autoreview/issues/466))
- A pull request whose review waits for approval no longer stops every discovery pass when its direct read fails: before, one such pull request (for example one moved to a base branch that autoreview does not support) failed each pass with `discovery poll failed`, and no other pull request in any repository got a review. Now a wait whose pull request the search rejects as `base_branch_unsupported` or `review_request_event_missing` ends as `superseded`, and any other read error is logged as `approval wait unreadable` and keeps the wait for the next pass. ([#475](https://github.com/pohunekd/autoreview/issues/475))

### Security

- **Breaking:** A `checkout: head` review now starts its pohunek session with `--no-repo-hooks`, so a pull request's own pohunek and git hooks never run on the review host, and it is refused before any session starts on a host without that switch (pohunek older than 0.43.1, `review_host_repo_hooks_unsupported`). The new required key `pohunek.head_checkout_host_hooks` (`refuse` or `allow`) decides whether such a review may run on a host whose own hook scripts would run in the worktree (`review_host_hooks_refused`); add it to an existing `config.yaml` before upgrading, and `scripts/env-to-config` reads it from the new required variable `HERMES_PR_REVIEW_HEAD_CHECKOUT_HOST_HOOKS`. ([#399](https://github.com/pohunekd/autoreview/issues/399))
- **Breaking:** `autoreview validate` refuses a store whose directory or files grant the group or other users any access, with `configuration_invalid` naming `store.path` and the `chmod` that fixes each path; it changes no mode itself. autoreview creates a missing store database with mode 0600 whatever the umask, `autoreview init` creates its `--dir` with mode 0700 when the store lies inside it, and `scripts/setup` runs `init` under `umask 077` and sets `UMask=0077` in its user units. Before the upgrade, make an existing store private as its owner, or `validate` stops, and with it `scripts/setup` (exit code 9) and `deploy/install.sh` (exit code 4): on a setup deployment made under the common umask 022, whose 0755 directory and 0644 store let other local users read the review history, run `chmod 700 DIR` and `chmod 600 DIR/autoreview.db*` with the `--dir` you gave setup (for example `~/autoreview`); for a store that a command run by hand created (install path a, or a path b store first opened with `sudo -u autoreview`), run `sudo -u autoreview sh -c 'chmod 600 /var/lib/autoreview/autoreview.db*'`, which expands the glob as `autoreview`, the only user who can list that 0700 directory. ([#439](https://github.com/pohunekd/autoreview/issues/439))
- Reviewer and verifier requests write U+0085 (next line) in pull request discussion, linked issues, prior findings and claims as the JSON escape `\u0085`, like U+2028 and U+2029, so a reader that ends a line at it cannot see a line the engine did not write. The JSON that `autoreview` commands print escapes U+0085 the same way. ([#432](https://github.com/pohunekd/autoreview/issues/432))
- Claude reviewer and verifier runs now pass `--strict-mcp-config`, so they load no MCP server: before, a server registered in the Claude user scope of the review host (for example `autoreview mcp` with a `write` token, or one with mail or chat access) or by a plugin could be loaded into a run that reads untrusted pull request text, and a `.mcp.json` that a `checkout: head` pull request adds is now skipped too. A base profile that sets `--strict-mcp-config` itself is now refused as a wrapper-controlled option. The change reaches a review host only when its profiles are installed again with `autoreview profiles install`. ([#448](https://github.com/pohunekd/autoreview/issues/448))
- Codex reviewer runs now pass `project_doc_max_bytes=0`, so Codex reads no `AGENTS.md` file of the review checkout as an instruction: before, the `AGENTS.md` files that a `checkout: head` pull request adds or changes became instructions of the review run. The reviewer still reads the repository's guidance from the trusted base as the prompt tells it. A `.codex/config.toml` in the checkout is not loaded either, because Codex reads it only for a project that the host's system or managed configuration trusts; the docs now say so. Repository skills of the checkout are covered by #454, which refuses a `checkout: head` pull request that adds or changes one. The change reaches a review host only when its profiles are installed again with `autoreview profiles install`. ([#449](https://github.com/pohunekd/autoreview/issues/449))
- Codex reviewer runs now refuse a `checkout: head` pull request that adds or changes a repository skill (`.agents/skills/` or `.codex/skills/`, compared on disk with the trusted base, so also as a link, an ignored file, a nested repository or a file that an index flag hides from git) before Codex starts, with `refused:repository_skills` before the exit line, and pass `skills.include_instructions=false`: before, Codex 0.167.0 loaded those skills without host trust, listed them on every turn and injected the whole `SKILL.md` of a skill that the prompt names, so a pull request could add instructions to its own review. The engine stops such a review at the first refused attempt with the new code `review_head_skills_refused`, which is not retried, and publishes nothing (#457); a `checkout: base` review and a head whose skills match the trusted base run as before. The change reaches a review host only when its profiles are installed again with `autoreview profiles install`. ([#454](https://github.com/pohunekd/autoreview/issues/454))

## 0.4.0 - 2026-11-15

### Added

- `--env-file <path>` gives the secrets of the `*_env` keys in a file of `NAME=value` lines, for a caller that starts autoreview with an empty environment, such as a pohunek workflow plugin. The file must be owned by the user that runs autoreview and give the group and others no access; a name in the file wins over the same environment variable, and its values are never added to the environment of autoreview, so no child process inherits them. ([#6](https://github.com/pohunekd/autoreview/issues/6))
- `publish.marker` names the two hidden markers of every published review: `autoreview` writes `<!-- autoreview:v1:...-->`, and `hermes-pr-review`, also used when the key is absent, keeps `<!-- hermes-pr-review:v1:...-->` for merge gates that read it. A retry after a lost acknowledgement finds the review under either name, so changing the key never posts a review twice. ([#7](https://github.com/pohunekd/autoreview/issues/7))
- `validate` and `serve` run `pohunek --version` on the CLI at `pohunek.bin`: `validate` prints `pohunek_version` and `serve` logs it as `pohunek version checked`. A release outside the supported range, 0.41.0 or later and before 1.0.0, fails with `pohunek_version_unsupported`, and a run that fails or prints no `pohunek X.Y.Z` with `pohunek_version_invalid`; both name `pohunek.bin`. ([#9](https://github.com/pohunekd/autoreview/issues/9))
- `github.credentials` accepts several credentials and `match` patterns other than `*`: each repository is served by the first credential whose `match` covers it. A `match` entry that an earlier one covers fails as `configuration_invalid`, a policy repository without a credential as `credential_not_covered`, and a credential that serves none as `credential_unused`. ([#13](https://github.com/pohunekd/autoreview/issues/13))
- `serve` checks every credential's token with GitHub before it starts and logs each token's expiry; a token that GitHub refuses fails with `credential_invalid` and a token of another account with `credential_login_mismatch`, each naming the credential. `validate --check-credentials` runs the same check and prints each credential's `name`, `login` and `expires_at`; without the option, `validate` still makes no GitHub call. ([#15](https://github.com/pohunekd/autoreview/issues/15))
- `serve` and the other engine commands accept several credentials in `github.credentials`, so repositories can be reviewed with a fine-grained token per owner or repository, or by another account per owner. With several credentials each credential's search, in a discovery pass and in the review queue, gets one attempt, so a failing token does not delay the repositories of the others. ([#18](https://github.com/pohunekd/autoreview/issues/18))
- `serve` checks every credential's token again while it runs, once when the engine starts and then every `github.credential_check_hours`, and logs each accepted check as `credential checked`; `github.credential_check_hours` above 8760 and `github.expiry_warning_days` above 366 are refused as `configuration_invalid`. A token that expires within `github.expiry_warning_days` raises the new `credential_expiring` event, at most once a UTC day per credential while `serve` runs (a restart warns again); the message names the credential and the expiry. The event is optional in the policy and defaults to `action`, so existing policies keep loading with the same digest. ([#19](https://github.com/pohunekd/autoreview/issues/19))
- A credential whose token GitHub refuses while `serve` runs is suspended: the new `credential_invalid` event (optional in the policy, default `action`) is raised once, its repositories are not searched and its queued reviews wait, while the other credentials keep reviewing. A search that GitHub refuses checks that credential's token right after the pass, and after every pass the token of each suspended credential is checked again; a check that GitHub accepts lifts the suspension. A GitHub call answered with HTTP 401 now fails as `credential_invalid` instead of `github_request_failed`: the step is retried within `schedule.step_retry_seconds`, then the review stops and is not retried automatically. ([#19](https://github.com/pohunekd/autoreview/issues/19))
- Notifications can go to a `none` backend, which only logs each message, and to a `webhook` backend that posts to Slack, Slack-compatible services, Discord or your own JSON receiver; the webhook URL is read from the variable that `url_env` names and never appears in logs or errors. A webhook request follows no redirect and sends no `Referer`, so a `3xx` answer fails with `webhook_request_rejected`. ([#29](https://github.com/pohunekd/autoreview/issues/29))
- A notification route and `notify.review_queue.backends` may name several backends; a failing backend no longer stops the others, and on a route with several backends a review resumed after a shutdown sends an `action` message only to the backends that have not taken it. The warnings of dropped notifications name the backend. ([#30](https://github.com/pohunekd/autoreview/issues/30))
- The release archive carries `deploy/install.sh` and hardened systemd units that run autoreview as the system user `autoreview`. The installer can run again without changing anything that is in place, runs `validate` as that user before it replaces the binary or a unit or restarts the service, and the units pass the secrets only through `--env-file`. ([#39](https://github.com/pohunekd/autoreview/issues/39))
- A clean review of an auto-approving rule waits for a person when the pull request matches a new `human_review` signal: a changed path, a line or file count, a note count or an author. The review body and the notification name each matched signal. ([#57](https://github.com/pohunekd/autoreview/issues/57))
- The optional `pohunek.host_state` section picks review hosts by the state that the `moc.host-state` pohunek plugin reports, read once per host and discovery pass: it can skip a host on battery, below a battery charge or free memory limit, without a required local model or outside its policy window, try idle hosts first, and decide what a host with an unknown state does. When only a held-back host has the repository, the review waits for a review host with `host_state_ineligible`; a repository pinned by `route_overrides` is not filtered. ([#180](https://github.com/pohunekd/autoreview/issues/180))
- `autoreview serve` answers `GET /metrics` in the Prometheus text format when `config.yaml` has a `metrics` section: gauges of the queued, running and awaiting reviews and the stopped pull requests, and counters and a publication time histogram of the reviews it runs, on the numbers of `autoreview stats`. Without the section `serve` opens no port. ([#235](https://github.com/pohunekd/autoreview/issues/235))
- `autoreview stats` prints review statistics from the store: reviews queued, running and awaiting approval per repository and review host and, with `--since`, daily counts over UTC days (started, published, approved without a human, changes requested, superseded, failed, and the median and p90 time to publication) per repository, rule and reviewer; `--json` prints the versioned document that the new read-scope MCP tool `review_stats` also returns. ([#235](https://github.com/pohunekd/autoreview/issues/235))
- The statistics document of `autoreview stats --json` and the MCP tool `review_stats` counts the stopped pull requests, whose attempts are used up or whose failure is not retried (`current.stopped`, per repository), and the failed attempts of the range per error code (`history.failed_by_code`). ([#235](https://github.com/pohunekd/autoreview/issues/235))
- A `checkout: base` review fetches the pull request head when its session starts, so fork pull requests and freshly pushed branches are reviewed without a manual `git fetch`; this needs pohunek 0.43.0 or later as the CLI and on the review host, and with an older pohunek reviews start as before. ### Security

- **Breaking:** A Codex review can no longer publish a result that the Codex transcript forged, for example a result frame and exit line that the model printed while it paused: the engine sends a fresh nonce with every Codex run, the adapter keeps it from the model and writes it into its markers, and the engine reads only markers with that nonce. Run `autoreview profiles install` for every Codex profile before you update the engine: an adapter from an earlier release refuses every Codex request before Codex runs, and the review fails with the new code `review_nonce_mismatch`. Claude profiles need nothing. ([#408](https://github.com/pohunekd/autoreview/issues/408))
- Model text in a published review can no longer publish a mention, raw HTML or an image through Markdown that GitHub reads as text where autoreview kept it as code: fenced blocks are written again with autoreview's own fence, an inline code span is kept only when its content is harmless as text, one-line fields such as titles keep no code, HTML entities are shown as written, footnote syntax is escaped so that no model text follows the AI signature, a mention is defused whatever comes before it, and the location of a finding is a paragraph of its own. ([#35](https://github.com/pohunekd/autoreview/issues/35))
- The `gh` and `pohunek` processes that autoreview starts inherit only an allowlist of the service's variables (`PATH`, `HOME`, `TMPDIR`, the `XDG_*` directories, and the config, proxy, CA and telemetry variables of `gh` or the remote port of `pohunek`), so a token of another tool in a shared environment file no longer reaches them. Every other variable, for example `GITHUB_TOKEN`, `GH_HOST`, `GH_DEBUG`, `LANG` or `TZ`, is no longer passed; see the secrets page for the full list. ([#202](https://github.com/pohunekd/autoreview/issues/202))
- Model text in a published review can no longer reference an issue, pull request or discussion of another repository, which GitHub records in that repository's timeline, or a commit there: `owner/repo#12`, `owner/repo/issues/12`, GitHub URLs to them and `owner/repo@sha` get a zero-width space, while references to the reviewed repository (`#12`) still link. A link reference definition in model text is escaped, so it cannot turn engine text such as a login into a link. ([#338](https://github.com/pohunekd/autoreview/issues/338))
- File paths that the review body and the notification name for human review signals, and the path of a finding in the review body, show each bidi control and zero-width character as `<U+XXXX>`, so a file name can no longer display as a different name than it has. ([#348](https://github.com/pohunekd/autoreview/issues/348))
- Model text in the review body, its kept code spans and fenced blocks, and the finding paths in the notification show each bidi control and zero-width character as `<U+XXXX>`, so model output can no longer display differently from what it holds; the zero-width spaces that defuse mentions and references stay invisible. ([#356](https://github.com/pohunekd/autoreview/issues/356))
- Pull request titles, model summaries, finding titles and paths, notes and logins in notifications and in the review queue stay on one line and show each bidi control and zero-width character as `<U+XXXX>`, so such a value can no longer forge a message line or display differently from what it holds; an excerpt cut never splits a `<U+XXXX>`. ([#359](https://github.com/pohunekd/autoreview/issues/359))
- `deploy/install.sh --root DIR` refuses a DIR, or a directory under it that holds an installed path, that a user other than you or root owns or that group or others can write to, and prints a `chmod go-w` command for a writable one. Such a user could otherwise swap a directory for a symlink after the check and redirect a write outside DIR. ([#365](https://github.com/pohunekd/autoreview/issues/365))
- The threat model no longer says that a review host project without setup hooks protects a `checkout: head` review: pohunek reads the in-repo hooks (`.pohunek/hooks/<event>`, `.pohunek/setup`) from the review worktree, so on a head checkout every in-repo hook, and any code it runs, is the pull request's code and runs on the review host. Give a head checkout only to authors who may run code on the review host; `checkout: base`, which every untrusted author gets, keeps the pull request's hooks out of the worktree. ([#399](https://github.com/pohunekd/autoreview/issues/399))
- A process that a Codex review run leaves behind can no longer write after the Codex adapter's result markers: when Codex exits, the adapter ends every process below it, also one that forked twice or started its own session (the adapter's children get `SIGTERM`, every process still left gets `SIGKILL` after 2 seconds), and stops copying Codex's stderr before it prints a marker with the run's nonce. The fix is in the adapter that `autoreview profiles install` writes, which now needs Linux (`PR_SET_CHILD_SUBREAPER`) and exits with status 64 elsewhere, so run it for every Codex profile after the update. Claude profiles need nothing. ([#413](https://github.com/pohunekd/autoreview/issues/413))

- The Codex adapter ships in `adapters/codex/`: a wrapper that runs one bounded, read-only Codex review for a pohunek session and prints a result frame, and a renderer that writes its pohunek profile. The Codex path comes from configuration, telemetry is optional, and the report now carries the blocking flag of each finding and verdicts on prior findings, which the engine reads from a later release. ([#22](https://github.com/pohunekd/autoreview/issues/22))
- `autoreview profiles install` writes, on the review host it runs on, the pohunek agent profile of a reviewer and the Claude or Codex adapter that it starts, both embedded in the binary. It pins the official runtime package, takes the model, the effort, the agent executable and the adapter limits as required flags, keeps identical files, rewrites the files it wrote earlier and refuses any other profile of that name unless `--replace` is given. The Codex adapter sets a terminal title before it reads its request, which pohunek's input readiness for Codex waits for, and accepts the trailing `--no-daemon` that pohunek appends to every Codex launch. ([#25](https://github.com/pohunekd/autoreview/issues/25))

### Changed

- **Breaking:** A `codex-envelope` reviewer reports notes that do not block and settles the earlier blocking findings, as a `claude-structured` reviewer does, so a Codex re-review after a push covers only the new commits. A Codex profile must run the adapter in `adapters/codex/`: the report of an older adapter, without `blocking` and `prior_findings`, stops the review with `review_adapter_outdated`. Switch every Codex profile to that adapter in the same maintenance window as this upgrade; a rollback to the Go engine needs the older wrapper back, and a Codex review in flight with prior findings stops. ([#23](https://github.com/pohunekd/autoreview/issues/23))

### Fixed

- **Breaking:** A review on a `checkout: base` pipeline whose pull request head commit is not in the review host's repository stops with the new code `review_head_unavailable` and publishes nothing, for Claude and Codex reviewers, instead of a Claude review that could not read the change; a verifier refused that way publishes the claims unverified, as after a verifier timeout. Neither the reviewer run nor the scheduler retries the stop; fetch the head on the review host and retry the pull request. The Claude adapter now checks the review checkout as the Codex adapter does and names that checkout in its result, and the engine refuses a Claude result without it as `review_adapter_outdated`, so run `autoreview profiles install` for every Claude and Codex profile on each review host in the same window as the upgrade. ([#253](https://github.com/pohunekd/autoreview/issues/253))
- A `codex-envelope` pipeline reviews the whole pull request again after a rebase, a force push or a merge of the base branch, as a `claude-structured` pipeline does, so a rule with `on_clean: approve` no longer approves a rewritten history on an incremental review. ([#237](https://github.com/pohunekd/autoreview/issues/237))
- A review that is due while a review host fails and no other host has the repository waits for a host instead of using its retries: it starts on the first discovery pass after a host answers, without `autoreview retry`, and one `review_stopped` message per host outage says that reviews wait for a review host. ([#241](https://github.com/pohunekd/autoreview/issues/241))
- Codex reviewers work on pipelines with `checkout: base`, which the examples use and untrusted authors require: the Codex adapter checks the base checkout locally and Codex reads the change through git. The pull request head must already be in the review host's repository; otherwise the review stops with `review_head_unavailable` (#253). ([#252](https://github.com/pohunekd/autoreview/issues/252))

### Security

- **Breaking:** The `--version` probe of the Claude and Codex adapters runs the agent executable with the environment of a review run, without the pohunek session identity, the GitHub and Matrix tokens and the `AUTOREVIEW_` variables. The adapters' `render_profile.py` copies only the telemetry keys (`OTEL_*`, and `CLAUDE_CODE_ENABLE_TELEMETRY` for Claude) and the config home (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`) of the base profile's `[env]`, drops every other key and prints the dropped names on stderr, so a profile rendered again loses any other variable it carried. Run `autoreview profiles install` for every Claude and Codex profile after the upgrade, and render again every profile written with `render_profile.py`. ([#246](https://github.com/pohunekd/autoreview/issues/246))

## 0.1.0 - 2026-11-09

### Added

- `autoreview init --dir --login --pohunek-host --example` writes `config.yaml`, the example's `policy.yaml` and its prompts into a directory, creating the directory (not its parent) when absent, prints the agent profiles the policy needs, and never overwrites a file. ([#8](https://github.com/pohunekd/autoreview/issues/8))
- A repository rule can now trust only some authors: `authors.trusted` lists logins (a user as `name`, an app as `name[bot]`, matched by author type), a repository permission or both, and an untrusted author, or the author of a fork pull request who is not listed, is skipped or reviewed under the `untrusted` section from the base checkout and is never approved without the user. The class is resolved when a review is dispatched, stored with it, and logged on the `review scheduled` line. ([#34](https://github.com/pohunekd/autoreview/issues/34))
- `autoreview mcp` serves the review commands as MCP tools over Streamable HTTP, so agents can list and read reviews and, with a write token, resolve, approve and retry them. It is off until the new optional `mcp` section is configured. A present section needs every key (the listen address, the allowed hosts, the timeouts and limits, and the clients with the SHA-256 digests of their tokens), and every command refuses an incomplete one at load. ([#179](https://github.com/pohunekd/autoreview/issues/179))
- `notify.routes` in `config.yaml` accepts an event name as a key next to `action`, `digest` and `log`, so a single event, such as `approved`, posts to its own Matrix room while every other event keeps the route of its level. The level still decides the mention and whether a failed message is dropped. A key that names no event, or a backend that is not configured, is refused at load with `configuration_invalid` naming `notify.routes.<key>`. ([#187](https://github.com/pohunekd/autoreview/issues/187))
- Each release ships a static Linux binary for `x86_64` and `aarch64` as `autoreview-<version>-<target>.tar.gz`, with a `.sha256` file and a build provenance attestation. The install guide makes this archive the default install path and shows how to check the checksum and the attestation. ([#222](https://github.com/pohunekd/autoreview/issues/222))

### Changed

- **Breaking:** A reviewer whose `finding_prefix` is `P` now fails the policy check, because `P` numbers the prior findings published again. Change that reviewer to another uppercase letter. ([#11](https://github.com/pohunekd/autoreview/issues/11))
- **Breaking:** Every repository rule of the policy now needs an `authors` section, and a policy without one is refused at load with `authors is required`. To keep reviewing every author as before, forks included, add `authors: {trusted: any}` to each rule. ([#32](https://github.com/pohunekd/autoreview/issues/32))
- **Breaking:** `session.name_prefix` and `session.branch_prefix` now name the pohunek sessions and reviewer branches. Set them to `github-review-` and `autoreview/review/` to keep the names of earlier releases, and change them only while no review runs, because a running review finds its session by name. A `session.branch_prefix` that cannot be part of a git ref name, or a prefix with a control character, is refused with `configuration_invalid`. `publish.signature` is published as written, so the example no longer shows a `{login}` placeholder. ([#193](https://github.com/pohunekd/autoreview/issues/193))
- The example `config.yaml` now loads as it is: its notifications and the review queue go to one placeholder `matrix` backend instead of a `none` backend that the loader refused. CI checks that every example policy loads with it. ([#36](https://github.com/pohunekd/autoreview/issues/36))
- When a rule runs several reviewers, a finding that two of them report on the same path, line and severity is published once, under the first reviewer's ID and with every reviewer's label. The review shows one summary, the first reviewer's, and one list of the validation performed without duplicates. ([#174](https://github.com/pohunekd/autoreview/issues/174))
- Published reviews are shorter: a non-blocking note shows only its heading and the `path:line` the reviewer reported (a note the verifier demoted keeps its body with the reason), and the list of validation performed is collapsed. Every reviewer request now states the summary, title and body limits from `limits`, and a Claude request also the limit of each prior-finding note. ([#175](https://github.com/pohunekd/autoreview/issues/175))
- The review host is the first host of `pohunek.hosts` whose projects serve the repository, so a repository registered on several hosts is reviewed there instead of failing with `project_route_ambiguous`. A host that fails is skipped with the warning `review host skipped` and the next host is asked, so one host outage no longer stops the reviews of repositories that other hosts serve. A repository that a trusted host also serves, for example through an `auto` project source, now runs there instead of failing, so pin untrusted repositories with `route_overrides` or keep `auto` out of their `project_sources`. ([#180](https://github.com/pohunekd/autoreview/issues/180))
- `config.yaml` accepts one Matrix backend per notification level and one for the review queue, so each level posts to its own room as the Go engine does. These backends must share `homeserver_url`, `access_token_env` and `mention_user`; a backend that differs is refused with the first route key, in the order `action`, `digest`, `log` and review queue, whose backend differs from an earlier one. ([#185](https://github.com/pohunekd/autoreview/issues/185))

### Fixed

- Reviews created within the same second are listed and resumed in the order they were created, and pruning compares the last update with the retention cutoff by time, so a review at the boundary is no longer kept or deleted by mistake. ([#120](https://github.com/pohunekd/autoreview/issues/120))
- An approval sent right after the approval request is accepted instead of failing with `review_not_awaiting_approval`, because the review is stored as waiting before the request is sent. When the approval request cannot be delivered, the review keeps waiting and `autoreview awaiting` lists it, instead of failing the review. ([#143](https://github.com/pohunekd/autoreview/issues/143))
- A review queue routed only to `none` backends is refused at load with `notify.review_queue.backends: none is not supported for the review queue`, and an empty list with `notify.review_queue.backends: must name at least one backend`, in place of the unrelated `invalid Matrix queue room`. ([#182](https://github.com/pohunekd/autoreview/issues/182))
- Discovery no longer fails when a label search finds no pull request or returns a `null` field or list entry, and a `null` value in a GitHub or pohunek response field is read as the Go engine reads it. ([#192](https://github.com/pohunekd/autoreview/issues/192))
- A reviewer output that breaks one of the engine checks (findings list, pull request and head, summary length, finding and test counts, a finding's id, side, line, path, title, body, confidence or severity, or a test's text) gets a fresh reviewer run up to the run limit instead of failing the review as `artifact_invalid`, and the log names the failed check. ([#196](https://github.com/pohunekd/autoreview/issues/196))
- The example policies no longer route `credential_invalid` and `credential_expiring`, events the engine does not know. The docs no longer describe `--env-file`, `prune-branches`, webhook backends, several backends per level or routes to `none`, and say that a route to a `none` backend is refused at load. ([#209](https://github.com/pohunekd/autoreview/issues/209))
- An unreachable notifier no longer stalls discovery: a discovery pass saves its state and queues due reviews first, then sends each notification once, skips the rest of a level after one fails at any level, sends nothing after a shutdown, and logs every undelivered one as `discovery notification dropped` without resending it. Every retry of a step is logged as `step failed, retrying` with the step, the error code and the delay. ([#210](https://github.com/pohunekd/autoreview/issues/210))
- An unreachable notifier no longer holds or fails a review: each notification of a review gets one attempt, and an undelivered one is logged as `review notification dropped` while the review goes on without resending it. `autoreview review-queue` posts its digest once and fails with the backend's error code, logged as `review queue digest dropped`, instead of retrying for the whole step budget. ([#212](https://github.com/pohunekd/autoreview/issues/212))
- A reviewer session whose worker pohunek reports as lost during the start now fails with the retryable code `pohunek_session_lost`, logged with pohunek's loss cause, instead of `session_identity_invalid` or `pohunek_session_cleanup_failed`. The explanations of `pohunek_base_fetch_timeout` and `pohunek_base_fetch_authentication_failed` name the SSH agent, and the troubleshooting runbook gains checks for inotify watches, non-interactive Git access and fetching over HTTPS. ([#213](https://github.com/pohunekd/autoreview/issues/213))

### Security

- The `gh` and `pohunek` processes that autoreview starts no longer inherit any `AUTOREVIEW_*` variable, any variable named by a `*_env` key or the Go engine's `MATRIX_ACCESS_TOKEN`; a `gh` call still gets the token of its credential as `GH_TOKEN`. ([#184](https://github.com/pohunekd/autoreview/issues/184))
